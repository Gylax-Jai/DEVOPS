# Kubernetes Basic Notes

Kubernetes is also called K8s.

Kubernetes is a tool used to run and manage containers. it solves problem of, scalablity(increase pods if high traffic), loadbalacning(divide traffic between multiple pods), high availability(if 1 cluster have 4 nodes , and one node get destroyed it will auto transfer all pods to other nodes)

Load Balancing: Distributing the traffic fairly across all Pods.
Auto-Scaling: Watching the traffic/CPU and spawning new Pods dynamically.
Auto-Healing: Constantly monitoring the Pods and instantly recreating any that crash or get deleted.
High Availability:
Worker HA: Never relying on one machine. If a Worker VM dies, the Pods shift to the surviving VMs.
Master HA: Using consensus algorithms (like Raft in etcd) so the surviving Master VMs vote and maintain total control of the cluster if a Master dies.

Docker is used to create and run containers.
Kubernetes is used to manage containers in a better way, especially when there are many containers or many servers.

## Docker vs Kubernetes

Docker:

Run this container.

Kubernetes:

Keep this app running like I described.

Example:

Docker command:

docker run -p 3000:3000 my-app

Kubernetes command:

kubectl apply -f k8s/

## Main Idea

In Docker, we directly run a container.

In Kubernetes, we create instruction files.

These files tell Kubernetes:

- which image to run
- how many copies to run
- which port to use
- how services should connect
- how to expose the app
- what to do if something crashes

Then Kubernetes follows those instructions.

## Service

Pods can stop, restart, and get new IP addresses.

So we use Service.

Service gives a stable address to access Pods.

Service can also expose our app to outside users.

Simple meaning:

Service = stable way to reach Pods

Flow:

User
-> Service
-> Pod
-> Container
-> App


The 3 Service Types
ClusterIP (Internal Only):
What it is: A fake, permanent IP address for Pod-to-Pod communication inside the cluster.
Analogy: The internal office intercom. External users cannot use it.

NodePort (The Backdoor):
What it is: Opens a specific port (like 30005) on the actual IP address of all your Worker VMs.
Analogy: A backdoor directly into the side of the building. (Mostly used for testing or Bare-Metal servers).

LoadBalancer (The Front Door):
What it is: Tells AWS/Google Cloud to create a massive, public-facing Load Balancer URL that routes internet traffic safely to your NodePorts.
Analogy: The main hotel entrance for the public internet.

ClusterIP vs Flannel IP
Flannel IP (The Raw IP): The actual, physical IP address assigned to a Pod (e.g., 10.244.1.5). If the Pod dies, this IP vanishes forever. Flannel builds the "roads" that allow these IPs to talk across different VMs.

ClusterIP (The Fake IP): A permanent, virtual IP address (e.g., 10.96.0.50). Because Flannel IPs change constantly, you use the ClusterIP as a stable address. It catches the traffic and routes it to the living Flannel IPs.

# Practical Activity: Deploying Nginx to Local Kubernetes

## Goal
To experience Kubernetes auto-healing and load-balancing using an Nginx web server.

## Step 1: Write the Instructions (nginx.yaml)
We created a Deployment and a Service.
- The **Deployment** was instructed to maintain 
eplicas: 2 (2 identical copies of Nginx).
- The **Service** was set as a LoadBalancer mapping port 8080 to the containers' port 80.

## Step 2: Apply the Instructions
Command used:
kubectl apply -f k8s/nginx.yaml

The exact millisecond this command runs, Kubernetes reads the file, downloads the Docker image, and starts the Pods. 
(Commands like kubectl get pods are just read-only commands to watch the progress).

## Step 3: Test Auto-Healing
Command used:
kubectl delete pod <pod-name>

Result: Kubernetes instantly noticed the Pod was missing and spawned a brand new one to replace it in just 16 seconds. This is how K8s prevents downtime!

## Step 4: Deleting vs Scaling
- kubectl scale deployment my-nginx-deployment --replicas=0: This stops the Pods but keeps the Deployment instructions in Kubernetes memory.
- kubectl delete -f k8s/nginx.yaml: This completely erases the Deployment and Service from Kubernetes memory (cleaning up the cluster), but your local .yaml code file remains 100% safe on your hard drive!

## Note on Auto-Scaling
If traffic increases and CPU usage spikes, a tool called Horizontal Pod Autoscaler (HPA) can automatically increase the number of replicas (e.g., from 2 up to 10). The LoadBalancer instantly detects the new Pods and divides the incoming web traffic among them.

# Advanced Architecture & Enterprise Concepts

## 1. Clusters, Nodes, and VMs
- **Node**: A single physical machine or Virtual Machine (VM).
- **Cluster**: A group of Nodes connected together to act as one giant supercomputer.
- Example: If you have 3 VMs, you create **1 Cluster with 3 Nodes**.

## 2. Masters vs Workers (The Enterprise Way)
In production, a cluster is split into two types of machines:
- **Worker VMs**: These ONLY run your application Pods (React, Node, Mongo). They handle the heavy traffic.
- **Master VMs**: These DO NOT run application Pods. They only run the Kubernetes "Control Plane" (The Brain). They monitor the Workers and make decisions. This ensures that if the Workers are overwhelmed with 10 million users, the Master stays calm and online.

## 3. The Four Pillars of K8s Architecture
1. **Load Balancing**: Traffic comes in, and the Load Balancer divides it fairly across all running Pods.
2. **Auto-Scaling (HPA)**: If traffic increases, CPU usage spikes. K8s automatically creates more Pods to handle the load.
3. **Auto-Healing**: If a Pod crashes or is deleted, K8s instantly recreates it.
4. **High Availability (HA)**: 
   - *Worker HA*: If a Worker VM dies, all its Pods are instantly recreated on the surviving Worker VMs.
   - *Master HA*: Enterprise clusters use 3 Master VMs. They use a consensus algorithm to vote and elect one "Leader." If the Leader Master dies, the other two Masters instantly vote to elect a new Leader, preventing any loss of control.

## 4. Leader Election Details
- You can send kubectl commands to **any** of the 3 Master VMs.
- However, behind the scenes, only the elected **Leader** makes the scheduling decisions. The other Masters act as active backups, constantly syncing data so they are ready to take over if the Leader fails.

KUBERNETES CLUSTER

CONTROL PLANE / MASTER VM

kubectl
- Command-line tool used to send Kubernetes commands to the API Server.
- It can be installed on the master/control-plane VM or any machine that has cluster access.

API Server
- The entry point/gateway for all Kubernetes requests.
- Receives requests from kubectl, UI, CI/CD tools, and other clients.

etcd
- Persistent key-value database for Kubernetes.
- Stores cluster configuration, desired state, Pods, nodes, Secrets, and other cluster information.

Scheduler
- Selects the appropriate worker node/VM for a newly created Pod.
- Considers available CPU, memory, node labels, taints, affinity rules, and more.

Controller Manager
- Continuously checks whether the actual cluster state matches the desired state.
- Example: if the desired state is 3 Pods but only 2 are running, it creates another Pod.


WORKER VM / WORKER NODE

Kubelet
- Agent running on every worker node.
- Receives Pod instructions from the API Server and ensures the required containers are running on that node.

Kube-proxy
- Manages network rules on the worker node.
- Helps Services route traffic to the correct Pods and supports load balancing.

containerd
- Container runtime.
- Pulls container images and starts/stops the actual containers.
- Kubelet uses containerd to run containers for Pods.

TO UPDATE THE APP USE ROLLING UPDATE PARAMETER

ROLLING UPDATE

Rolling updates replace old Pods with new Pods gradually.

maxUnavailable:
- Maximum number of Pods allowed to be unavailable during the update.
- maxUnavailable: 2 means up to 2 Pods can be unavailable.
- It does not control how many new Pods are created.

maxSurge:
- Maximum number of extra new Pods allowed during the update.
- maxSurge: 2 allows 2 additional new Pods temporarily.

strategy:
  type: RollingUpdate
  rollingUpdate:
    maxUnavailable: 2
    maxSurge: 2

HPA(horizontal scaling) and Metrics

HPA — Horizontal Pod Autoscaler

HPA automatically increases or decreases the number of Pod replicas based on metrics such as:

- CPU utilization
- Memory utilization
- Custom application metrics

Example:

kubectl autoscale deployment web-app \
  --min=2 \
  --max=10 \
  --cpu-percent=70

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: cisco-prod-app-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: cisco-prod-app
  minReplicas: 2
  maxReplicas: 10
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70

# Kubernetes & Container Runtime Study Notes

## 1. Do We Need Docker Desktop for Kubernetes?
No. Modern Kubernetes (v1.24+) does not require Docker.
Kubernetes deprecated dockershim and now talks directly to lightweight container runtimes through the CRI (Container Runtime Interface).
In production and Linux servers, Kubernetes runs natively on top of **containerd**.

## 2. The Core Setup Components (From Scratch)
When building a raw Kubernetes node/cluster on Linux, you need 4 primary pillars:

| Component | What it is | Role / Responsibility |
|-----------|------------|-----------------------|
| **containerd** | Container Runtime | The low-level engine that pulls container images from registries and executes Linux containers. |
| **kubelet** | Node Worker Agent | Runs as a system service on every node. It receives instructions from the control plane and ensures the Pods/containers are running and healthy. |
| **kubeadm** | Cluster Bootstrapper | The CLI admin tool to initialize the cluster (kubeadm init on master node) and connect worker nodes (kubeadm join). |
| **CNI** | Container Network Interface | Third-party network overlay (e.g., Flannel, Calico, Cilium) that assigns unique IP addresses to every Pod so they can communicate across different physical servers. |

## 3. What is "Vanilla Kubernetes" (Vanilla K8s)?
- **Meaning**: It is NOT a downloadable app or specific software installer.
- **Definition**: It is an industry term / slang (like "Vanilla JavaScript").
- **What it refers to**: Running the pure, raw, unmodified open-source Kubernetes directly from the CNCF/upstream project using kubeadm on clean Linux servers without proprietary commercial layers or cloud wrappers.

## 4. Kubernetes Flavors Comparison

                     +-- Vanilla K8s (Raw open-source via kubeadm)
                      
Kubernetes Universe -+-- Managed Cloud (AWS EKS, Google GKE, Azure AKS)
                      
                     +-- Lightweight/Local (k3s, Minikube, Kind)
                      
                     +-- Enterprise Platforms (Red Hat OpenShift, Rancher)

- **Vanilla K8s**: 100% free, complete control, manual maintenance/upgrades.
- **Managed Cloud (EKS/GKE/AKS)**: Cloud provider manages master nodes and control plane automatically.
- **Lightweight (k3s/Minikube)**: Packaged single-binary distributions for local dev or edge computing.
- **Enterprise (OpenShift/Rancher)**: Vanilla K8s bundled with custom UI dashboards, enterprise security, and commercial support.
